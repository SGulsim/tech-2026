# Отчёт: сравнение типов кеширования

Сравниваются три стратегии работы приложения с кешем для одной и той же системы:

- **Cache-Aside** (Lazy Loading / Write-Around) — чтение через кеш с подгрузкой из БД, запись в БД с инвалидацией кеша.
- **Write-Through** — чтение через кеш, запись синхронно в кеш и в БД.
- **Write-Back** — чтение через кеш, запись только в кеш + dirty-buffer; в БД данные уходят фоновым флашером.

Стек: Node.js / TypeScript, Redis 7.2 (кеш), Postgres 16 (БД), всё в Docker. Нагрузочный генератор — самописный, на TypeScript, с детерминированной последовательностью операций (Mulberry32 PRNG, seed = 42), чтобы все стратегии прогонялись на абсолютно одинаковом потоке запросов.

---

## 1. Параметры теста (единый для всех вариантов)

| Параметр                 | Значение              |
| ------------------------ | --------------------- |
| Размер датасета (товары) | 200                   |
| Всего операций за прогон | 10 000                |
| Параллельных воркеров    | 50                    |
| Распределение ключей     | равномерное по 200 id |
| PRNG seed                | 42 (детерминированно) |

Перед каждым прогоном: `TRUNCATE products` + сид 200 строк, `FLUSHDB` в Redis, обнуление счётчиков. Это гарантирует, что разница между стратегиями — следствие именно стратегии, а не оставшегося горячего кеша от предыдущего теста.

Сценарии нагрузки (одинаковые для всех трёх стратегий):

| Сценарий      | Read / Write |
| ------------- | ------------ |
| `read-heavy`  | 80 / 20      |
| `balanced`    | 50 / 50      |
| `write-heavy` | 20 / 80      |

### 2.1 Демонстрация накопления буфера у Write-Back

Отдельный прогон `npm run writeback-demo` — 60 000 записей с **уникальными** id (чтобы ничего не сжималось), `flushInterval = 1000 мс`, batch = 500. Источник: `results/writeback-demo.log`.

```
 time(ms)   buffer   db_writes
      101     5853           0
      201    13065           0
      301    20568           0
      401    28459           0
      501    36448           0
      600    44562           0
      701    52769           0
                              ← writer закончил за 786 мс, max buffer = 52 769
      801        0        2000
      902        0       13500
     1002        0       26500
     1103        0       38500
     1203        0       49500
```

Что здесь видно:

1. Пока приложение писало с пиковой скоростью, **в БД не ушло ни одной записи** — флашер ещё не тикнул.
2. Буфер разрастался почти линейно — это та самая «угроза» write-back: при сбое процесса вся эта пачка несохранённых записей теряется.
3. После завершения нагрузки `shutdown` слил буфер пакетами в БД — обычно за это отвечает graceful shutdown / периодический tick.

## 3. Описание тестов

| Что меряли                     | Как меряли                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Throughput (req/sec)           | `totalOps / wallDurationSeconds` — реально достигнутый rps                                                       |
| Avg latency                    | средняя по всем операциям; отдельно средняя по read и по write                                                   |
| Cache hit rate                 | счётчики `hits` / `misses` в обёртке над Redis (`src/cache.ts`) — инкрементируются на каждый `GET`               |
| Обращения в БД                 | счётчики `reads` / `writes` в обёртке над `pg.Pool` (`src/db.ts`) — инкрементируются на каждый `SELECT`/`INSERT` |
| Накопление буфера у Write-Back | `strategy.bufferSize()` снимается каждые 100 мс в `writeback-demo`                                               |

Алгоритм бенчмарка (`src/benchmark.ts`):

1. Поднять Postgres + Redis (docker compose).
2. Для каждой пары (стратегия, сценарий):
   - `TRUNCATE products`, засеять 200 строк, `FLUSHDB`, обнулить счётчики.
   - Сгенерировать **детерминированную** последовательность 10 000 операций (id и read/write подбираются seeded RNG → одинаково для всех стратегий).
   - Запустить 50 параллельных воркеров, которые забирают операции из общего курсора и вызывают `strategy.get()` / `strategy.set()`.
   - Для write-back — после нагрузки дождаться, пока dirty-buffer полностью сольётся в БД (`strategy.shutdown()`).
   - Снять метрики, добавить в общий результат.
3. Распечатать сводную таблицу + сохранить JSON в `results/`.

## 4. Выводы

### Что лучше для **чтения**

**Write-Through** и **Write-Back** идут ноздря в ноздрю по hit-rate (~97 %), потому что в их случае и записи тоже кладут данные в кеш, и кеш почти не «остывает». Cache-Aside даёт всего 75 % hit-rate даже на read-heavy, потому что инвалидация при записи заставляет следующий `get` идти в БД.

Если важна **простота** + хорошее чтение — **Write-Through**: писатель сам подогревает кеш, нет асинхронных артефактов.
Если важна **максимальная скорость** чтения — **Write-Back** (нет блокирующих DB-write, latency ~0.6 мс).

### Что лучше для **записи**

С большим отрывом — **Write-Back**:

- 8000 логических записей превращаются в **200 строк в БД** (write-coalescing по уникальным id).
- Throughput на write-heavy: **82 000 rps** против ~8 000 у других стратегий — **в 10 раз быстрее**.
- Запись возвращает управление сразу после `cache.set()`, не дожидаясь Postgres.

Cache-Aside и Write-Through на write-heavy практически идентичны (~8000 rps), потому что обе бьют синхронно в БД на каждой записи. Cache-Aside дополнительно теряет hit-rate (19.6 %), что не критично на write-heavy, но сильно бьёт по последующим чтениям.

### Что лучше для **смешанной нагрузки** (50 / 50)

Снова **Write-Back** — 84 000 rps, 304 запроса в БД на 10 000 операций.
**Write-Through** — разумный компромисс (13 700 rps, 97 % hit-rate, **нет риска потери данных**).
**Cache-Aside** на balanced хуже всех (10 400 rps, hit-rate всего 47 % — ровно потому что половина операций — записи, и они выбивают ключи из кеша).

### Цена скорости Write-Back

Демо `writeback-demo` показало главный риск: **buffer of 52 769 записей** в памяти, которые ещё не дошли до БД. Если процесс упадёт в этот момент — данные теряются. Для прода Write-Back имеет смысл, когда:

- допустима _eventual consistency_;
- данные не критичны (метрики, счётчики, лайки);
- буфер защищён (durable write-ahead log, persistent queue, репликация);
- чёткий graceful shutdown с принудительным flush.

### Сводная рекомендация

| Профиль системы                                                                  | Оптимальная стратегия                               |
| -------------------------------------------------------------------------------- | --------------------------------------------------- |
| Много чтения, редкие записи, важна простота и консистентность                    | Cache-Aside (классика для каталогов и справочников) |
| Смешанная нагрузка, важно чтобы кеш всегда был тёплым и согласованным с БД       | Write-Through                                       |
| Очень высокая интенсивность записей, допустима небольшая задержка попадания в БД | Write-Back                                          |

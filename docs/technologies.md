# Технологии проекта: что, зачем и почему

---

## PostgreSQL — основная база данных

**Что хранит:** пользователей, анкеты, лайки, мэтчи, рейтинги, ключи фотографий.

**Почему PostgreSQL, а не например MongoDB:**
Данные в дейтинг-боте сильно связаны — лайк ссылается на пользователя и анкету, рейтинг ссылается на анкету, мэтч ссылается на двух пользователей. Реляционная БД с foreign key-ами гарантирует целостность: нельзя поставить лайк несуществующей анкете, нельзя удалить пользователя не удалив его профиль. MongoDB этого не контролирует.

**Оптимизации:** в моделях расставлены составные индексы:
```python
# likes — для подсчёта лайков/скипов в rating_service
Index("ix_likes_profile_skip", "to_profile_id", "is_skip")
# likes — для подсчёта активности за последние 7 дней
Index("ix_likes_profile_skip_time", "to_profile_id", "is_skip", "created_at")
# ratings — для ORDER BY final_score DESC при сборке очереди
Index("ix_ratings_final_score", "final_score")
```
Без этих индексов каждый пересчёт рейтинга и каждая сборка очереди делали бы `Seq Scan` по всей таблице лайков.

## Redis — кэш очереди просмотра

**Что хранит:** два ключа на каждого пользователя:
- `browse:{telegram_id}` — List, TTL 1 час — очередь из 10 profile_id для выдачи
- `seen:{telegram_id}` — Set, TTL 7 дней — id анкет, которые уже были показаны

**Зачем нужен Redis:**
Без кэша каждый свайп — это тяжёлый SQL-запрос с JOIN трёх таблиц, подсчётом лайков и сортировкой по `final_score`. С Redis этот запрос делается один раз на 10 анкет, а потом каждый свайп — просто `LPOP` из памяти: O(1), ~1 мс.

**Почему List + Set, а не одна структура:**
List — идеальная очередь: `RPUSH` добавляет в конец, `LPOP` забирает с начала (FIFO). Set нужен отдельно, потому что лайк пишется в БД **асинхронно** через RabbitMQ. Пока он не дошёл до базы, `get_ranked_profiles` не видит анкету как просмотренную и добавляет её в новую порцию повторно — именно это и вызывало дубли. Set фиксирует факт показа мгновенно, независимо от состояния БД.

## RabbitMQ — брокер сообщений

**Две очереди:**
- `profile.actions` — бот публикует лайк/скип → бэкенд забирает и обрабатывает
- `bot.notifications` — бэкенд публикует событие мэтча → бот забирает и отправляет уведомление

**Зачем брокер, а не прямой HTTP-вызов:**
Когда пользователь нажимает ❤️, бот немедленно отвечает и показывает следующую анкету — он не ждёт пока бэкенд запишет лайк в БД, пересчитает рейтинг и проверит мэтч. Это занимает время, а Telegram ждёт ответа на callback за ~1–2 секунды. Брокер разрывает эту связь: бот кладёт событие в очередь и идёт дальше, бэкенд обрабатывает в своём темпе.

**Надёжность:** сообщения отправляются с `delivery_mode=PERSISTENT` — они сохраняются на диск и не потеряются при перезапуске RabbitMQ.

## Celery + Celery Beat — фоновые задачи

**Что делает:** каждый час пересчитывает рейтинги всех анкет батчем.

**Зачем нужен Celery:**
Рейтинг пересчитывается и инкрементально (при каждом лайке через RabbitMQ), и батчем раз в час. Батч нужен чтобы подтянуть анкеты, у которых давно не было активности — их `level2_score` (активность за 7 дней) должен постепенно снижаться. Это нельзя делать в основном процессе FastAPI — он обслуживает HTTP-запросы, а не занимается периодическими задачами.

**Celery Beat** — встроенный планировщик, аналог cron внутри Celery. Запускается отдельным контейнером и отправляет задачу воркеру по расписанию.

**Retry-логика:** задача помечена `max_retries=3, countdown=60` — если пересчёт упал (например, БД временно недоступна), Celery повторит попытку через 60 секунд, до 3 раз.

## MinIO — хранилище фотографий (S3-совместимый)

**Что делает:** хранит загруженные фото пользователей. В БД хранится только `s3_key` и URL, сам файл — в MinIO.

**Зачем отдельное хранилище, а не в БД:**
Хранить бинарные файлы в PostgreSQL — плохая практика: это раздувает размер БД, замедляет бэкапы и усложняет репликацию. Объектное хранилище специально оптимизировано под большие файлы.

**Pre-signed URLs:** фотографии отдаются через временные ссылки (`X-Amz-Expires=3600`). Бот скачивает фото по ссылке и отправляет в Telegram через `BufferedInputFile` — пользователь видит фото, а не ссылку на MinIO.

**Почему MinIO, а не AWS S3:**
MinIO — это self-hosted реализация S3-совместимого API. Для локальной разработки и учебного проекта не нужен реальный AWS-аккаунт, при этом код полностью совместим — в продакшене достаточно сменить endpoint и ключи.

## structlog — структурированное логирование

**Что делает:** все логи пишутся в JSON-формате с контекстными полями, а не просто строками.

**Зачем структурированные логи:**
Обычный `print("like created")` бесполезен при отладке. Structlog пишет:
```json
{"event": "profile_liked", "by": 5, "profile": 15, "timestamp": "..."}
```
Такие логи можно фильтровать, агрегировать и отправлять в системы мониторинга (Grafana Loki, ELK). Каждое событие несёт контекст — кто, что, когда.

## Prometheus — метрики

**Что собирает:** HTTP-метрики всех эндпоинтов автоматически через `prometheus-fastapi-instrumentator` — количество запросов, latency по перцентилям, статус-коды.

**Зачем нужны метрики:**
Логи отвечают на вопрос "что произошло", метрики — "как система работает в целом". Например, если latency `/api/v1/browse` выросла с 10 мс до 500 мс — это видно на графике в Prometheus до того, как пользователи начнут жаловаться.

## aiogram 3 — Telegram Bot Framework

**Что делает:** обрабатывает сообщения и callback-кнопки через FSM (Finite State Machine).

**Зачем FSM:**
Создание анкеты — многошаговый диалог: имя → возраст → пол → город → интересы → bio → фото. FSM хранит промежуточное состояние пользователя (в каком шаге он находится) и данные между шагами. Без FSM нельзя понять, зачем пользователь прислал "25" — это возраст при создании анкеты или ответ на что-то другое.

## FastAPI — Backend Framework

**Зачем FastAPI, а не Flask:**
FastAPI построен на `asyncio` — все запросы к БД, Redis и MinIO выполняются асинхронно. Flask синхронный: пока один запрос ждёт ответа от БД, поток заблокирован и не может обрабатывать другие запросы. При одновременном использовании бота несколькими пользователями это критично.

Также FastAPI автоматически генерирует Swagger UI из Pydantic-схем — удобно для отладки и демонстрации.

## Docker Compose — оркестрация

**Что запускает:** 7 сервисов одной командой — postgres, redis, rabbitmq, minio, backend, bot, celery-worker, celery-beat, prometheus.

**Зачем контейнеры:**
Без Docker каждый разработчик должен вручную установить и настроить PostgreSQL, Redis, RabbitMQ и MinIO нужных версий. С Docker — `docker compose up --build` и всё работает одинаково на любой машине. Сервисы общаются по именам (`postgres`, `redis`) внутри Docker-сети, а не через `localhost`.
